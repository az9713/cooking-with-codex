The expert skill is closing the loop.

Both hosts repeatedly supply useful context, let Codex execute, inspect what actually happened and steer the next increment. Their demonstrations extend that loop through project goals, workers, durable notes, tools, hooks and scheduled follow-ups. Prompt length is secondary to the quality of the task contract and the evidence used to accept its result.

This guide gives you procedures to practice. Reading it alone cannot establish the hosts’ level of expertise; the proficiency checks below require working artifacts and observable results.

Inventory / required and optional parts

Start with the parts you have.

  • Codex desktop + a project folderA known working directory, current model available in your client, and a useful first outcome. A model name shown in the June demonstration is not a requirement.
  • A task contractOutcome, constraints, important unknowns and observable finish criteria. Include what matters to the intended user.
  • Context with provenanceRelevant repository files, document versions, appshots or screenshots, and exact source locators.
  • Execution and review toolsShell, structured connectors, browser and tests as available. Catalog entries do not prove access or configuration.
  • Durable project stateAGENTS.md for project rules; GOALS.md or equivalent for milestone criteria, evidence, decisions and blockers.
  • Optional extensionsSkills, plugins, worktrees, workers, hooks, automations and a custom client. Add them when a concrete task benefits.

Windows adjustment: Product documentation supports Windows computer use; it operates on the foreground desktop. Native tool availability depends on the client and configuration. It can move the pointer and type while you are using the same session. Keep ordinary inspection in a hidden browser. Reserve foreground control for tasks that actually need it. Windows behavior in the official documentation.

Context capture on Windows

Current documentation describes appshots using both Alt keys, with a configurable hotkey. An appshot includes an image and available application text, which may extend beyond the visible pixels. A regular screenshot supplies pixels; attach relevant text separately when needed. Verify the attachment before sending it. Appshots documentation.

Portable method, platform-specific implementation

The translator and Retrodex demos use macOS applications. Reproduce their product behavior in a Windows-compatible implementation, rather than copying Swift, macOS audio routing or shell paths. Connected-phone control still needs an execution host; the phone is not the build machine. Worktrees and handoffs.

01

Supply context that changes the result.

Gabriel’s appshot-led workflow + Charlie’s context model. 6:36 15:32

Observed: a Slack conversation and dictation precede the translator build. The short typed request has substantial attached context. A later slide puts tools, instructions, appshots and memory together.

  1. Open the relevant project and identify the actual outcome, user and constraints.
  2. Attach the useful source: appshot, document or code. Identify its date or version when that matters.
  3. State the acceptance criteria: a visible workflow, valid export, reproducible result or measured behavior.
  4. Ask Codex to inspect available tools and relevant files, then resolve only design-changing unknowns.
  5. Keep stable preferences in instructions; keep changing project facts and decisions in project files.

Why this works: the agent can infer a UI from a screen, but your constraints decide what to implement. A memory preference such as package-manager choice does not replace current repository evidence.

Try Context interview or Screen → brief. Memory labels and defaults in the video are historical; inspect your current settings.

02

Build a small complete artifact, then inspect it.

Charlie's repository visualization + Gabriel’s build-and-test loop. 9:17 13:04 19:28

  1. Ask for one useful end-to-end slice, including how it will be run and checked.
  2. Let Codex use relevant installed skills and plugins; verify their availability instead of assuming it.
  3. Exercise the main user path. Inspect the rendered output and the code changes.
  4. Report a concrete defect with a screenshot or reproduction, then steer the same task.
  5. Accept the result against its criteria and save the reusable method.

The IKEA request: ask for parts, their relationships, numbered assembly steps and the finished system. The source’s manual depicts Agent configuration, a Runner loop, optional tools/handoffs/MCP, results/streaming and surrounding capabilities. Use your repository’s actual structure, rather than inventing an architecture from those names.

Measure the thing that matters

A translator needs intelligible output, input routing, latency and recovery checks. A diagram needs agreement with the code. A working window proves only that the window runs; a code-review summary proves only what was actually reviewed.

04

Make complex work legible and verifiable.

Goals, research audits, worker ownership and critical-path blockers. 28:45 32:16 37:18 42:23

  1. Use a supported /goal workflow with an outcome, constraints and verification criteria. Use planning or an interview when the design is unresolved.
  2. Break the work into bounded milestones. The research example explicitly keeps one active milestone at a time.
  3. Write durable status: acceptance criteria, evidence, decisions, blockers and the next action. A dashboard is a view of these facts.
  4. Delegate genuinely independent jobs with owned files or responsibilities and required evidence. Keep integration accountable to the main task.
  5. Audit claims against the artifact before marking a milestone complete; reconcile README, goals and dashboard after fixes.

Official goals documentation. Try Goal contract, Bounded worker and Audit.

Handle a blocker precisely

The deployment example hits account and credential dependencies. Continue independent implementation and checks; then identify the smallest missing input and the work it unlocks. A vague “needs access” status is less useful than naming the service, operation and blocked milestone. Enter credentials through the service’s secure flow or an appropriate local mechanism, rather than putting them into a reusable prompt.

Choose the coordination unit

Subagent: a bounded job under the current task, with delegated context and a return result. The QA demo reuses a worker after a new screenshot arrives.

Visible chat: separately inspectable and steerable work, useful when you want a persistent owner or interface. Messaging other chats needs explicit user authorization. For concurrent code changes, use independent worktrees when useful, with an integration plan. Worktree documentation.

Compaction is not your source of truth

The hosts discuss maintaining continuity over long runs. Preserve important state in files so it can be re-read after compaction or handoff. Their continuity claims do not prove perfect recall of every earlier detail.

Research standard: the on-screen audit explicitly distinguishes a heuristic best-found result from a certified optimum. Ask for small-instance reference checks, numerical conventions and a clear account of what is empirical versus proven. 33:28

05

Repeat a proven workflow with a stop condition.

Hooks, heartbeats, feedback triage and workflow learning. 47:57 50:24 52:37

MechanismJob
HookDeterministic command at a lifecycle event: formatting, a focused check or a report. Verify event timing and timeout.
HeartbeatRevisit an ongoing task later, react to changed state and stop when the condition is resolved.
Scheduled automationRepeated independent work, such as a weekly review. Choose the actual execution environment.
SkillA reusable procedure invoked when its task applies; scheduling is a separate concern.

Local scheduled work needs the computer and app available for local files. A cloud execution environment has a different file/tool boundary. Automation documentation.

  1. Run the procedure once manually and establish the evidence that makes it successful.
  2. Choose an event-triggered command, task heartbeat or independent schedule according to the work.
  3. Define allowed actions, deduplication, failure handling and notification rules.
  4. Give it an observable completion or stop condition. Retain enough evidence to diagnose failures.
  5. After success, save the procedure as a skill if useful and remove completed monitors.

Hook adaptation: the visible Stop hook runs a Python repository-tidy script with a 20-second timeout. Its macOS command uses shell expansion. Inspect the installed schema and run your Windows command manually before configuring it; preserve existing hooks. Hooks documentation.

Evidence boundary: server provisioning visibly reaches a ready state and removes its monitor. Slack feedback-to-PR development is presented as setup and intent; the sampled evidence does not prove the whole pipeline completed. The presentation monitor uses heuristic predictions and a visible sleep, not a calibrated forecasting system.

Try One check as a hook, Bounded monitor, Feedback loop or Save a skill. Skill documentation.

06

Embed the harness when you need your own interface.

The optional developer track: App Server and Retrodex. 58:37

The source shows a custom native chat client with workspace, model, reasoning and run controls. This extends the operating method into a product interface. It does not make a native UI necessary for your everyday Codex work.

  1. Identify an interaction the existing client does not serve well.
  2. Inspect the installed App Server version and generate its protocol schema.
  3. Prove the minimal lifecycle before adding styling: initialization, thread, turn, events and interruption.
  4. Handle approval decisions explicitly and test the supported resume behavior.
  5. Build a Windows-compatible interface and verify the lifecycle end to end.

Try Minimal client. The Retrodex screen demonstrates a running turn; robust synchronization between clients is not established by that sample.

Protocol essentials, verified separately

Current documentation describes JSON-RPC-style messages, stdio JSONL transport by default, and the sequence initialize → initialized → thread/start → turn/start, followed by notifications. Generate TypeScript or JSON schemas from the installed version. WebSocket transport is documented as experimental; keep a minimal local client on the supported path. App Server documentation.

Boundary: a custom client changes the interface to the harness. It does not automatically supply every plugin, signed-in browser session, desktop capability or permission.

Reusable parts / original adapted prompts

A prompt kit you can use.

These are new prompts derived from the demonstrated workflows, not verbatim quotations from the hosts. Replace brackets and attach the relevant context. Start with the smallest prompt that matches the job.

Context interview

Use before a new project; attach the actual files or appshot.

I want to build [outcome] in my Windows Codex workspace. The intended user is [who], and the important constraints are [constraints]. Inspect the available files, tools and attached context first. Ask only questions whose answers would materially change the design; continue independent work while waiting. Give me a small first milestone with observable acceptance criteria, then implement it. Use a browser in the background for inspection; do not put it in full screen.
Turn a screen into a brief

Use an appshot plus your spoken or typed intent.

From this attached appshot and my notes, recover the intended workflow, data inputs, visible controls and missing decisions. Separate what you can actually see from inference. Build the smallest useful version for Windows. Before calling it complete, run it and exercise the main user path. Return the artifact, the check result and any remaining limitation.
Make a repository assembly manual

The closest replication of the video’s IKEA example.

Inspect this repository and its current documentation. Produce one self-contained HTML assembly manual in an IKEA instruction style: monochrome line diagrams, a parts list, numbered panels, connection arrows and a final assembled view. Explain the actual entry points, data flow, optional components and failure boundaries. Link each technical claim to the relevant file or official documentation. Mark inferred relationships. Check the diagrams against the implementation and render the HTML. Do not add features to the repository.
Choose and verify the action surface

Useful for browser QA and dashboard work.

Task: [specific browser outcome]. First identify which available tool can do it and where the relevant session is signed in. Prefer structured tools when available; otherwise use the isolated browser for local/public content or my signed-in Chrome for the named service. Keep inspection in the background. Verify the final visible state and save evidence. If the task requires foreground Windows desktop control, explain the concrete need before starting it.
Export data with a contract

Make the time window and schema explicit.

From [dashboard], export [metric] as CSV for [start inclusive] through [end exclusive], using timezone [zone], and [other metric] as JSON for [period]. Preserve the source’s filters and document them. Verify headers, row counts, date boundaries, units and totals against the visible source. Save both outputs locally with an export note. Report missing data rather than filling it in.
Document → draft form

Adapt the demonstrated transfer to your own questions.

Read [named document] and create a draft form in [named service] using its questions. Preserve wording, choices, order and required status. Check the editor and respondent preview, including invalid submission and one valid test response if a disposable test is available. Report the resulting draft link and discrepancies. Keep it a draft; publication is outside this task.
Set a verifiable goal

Invoke /goal in a supported client, then supply this contract.

Goal: [observable outcome]. Constraints: [scope, budget, platforms, prohibited changes]. Keep one active milestone and durable GOALS.md notes covering acceptance criteria, evidence, decisions, next actions and blockers. Complete the milestone only when its checks pass. If workers help, give each an independent scope and integrate their evidence. After a milestone, reconcile the documentation with the actual code and choose the next bounded milestone.
Replicate a paper rigorously

Designed for a research workbench, not a claim of automatic discovery.

Reproduce [specific claim or algorithm] from [paper/version/pages] on [dataset or small synthetic instances]. First record assumptions, objective, constraints, units, conventions and the exact claim. Establish a simple reference implementation and independent small-instance oracle where feasible. Compare outputs with tolerances justified by the method. Separate implementation correctness, empirical reproduction and theoretical guarantees. Preserve seeds, dependencies, commands and failures. Do not call a heuristic result globally optimal without a valid certificate or proof.
Delegate one bounded job

Use only when the main task actually benefits from a subagent.

Use a subagent for [independent task] with ownership of [files/responsibility]. Acceptance evidence: [check or artifact]. It is not alone in the codebase: it must preserve others’ edits and accommodate concurrent work. Give it the relevant context, an explicit stopping condition and the facts it must report. Keep integration and final verification with the main agent. Reuse an existing suitable worker before creating another.
Coordinate visible chats

This explicitly authorizes the named coordination.

Coordinate these existing Codex chats: [exact titles or IDs]. You may send each the scoped instructions needed for [specific project purpose]. Assign non-overlapping ownership, use worktrees where independent code changes require isolation, and maintain a short dashboard of owner, scope, last evidence, next action and blockers. Report integrated results after checking them; an idle worker alone is not proof of success.
Interrogate progress

Use a supported side conversation, or ask in the main chat.

What changed in the last working interval? What evidence supports the current status? What is on the critical path, what can proceed independently, and what exact input would unblock you? Answer concisely, then continue the authorized work. Put any durable decision back into the project’s main notes.
Audit before accepting completion

Ask for a fresh review perspective when justified.

Audit this milestone against its acceptance criteria and the actual artifact. Look for contradictions between implementation, tests, dashboard, README and reported guarantees. Exercise the important failure paths. For every finding give severity, concrete evidence and the smallest fix. After fixes, rerun the affected checks and state exactly what remains unverified.
Make one repeated check deterministic

No need for an elaborate hook framework.

The repeated step is [specific repository check]. Inspect my installed Codex version and existing hook configuration. Implement the smallest Windows-compatible deterministic command, with an appropriate timeout and useful failure output. Run it manually first. Then configure the appropriate lifecycle hook without overwriting unrelated hooks. Verify when it runs and demonstrate its failure and success behavior.
Monitor this task to completion

Use the app’s automation tool; do not emulate it with raw cron text.

Monitor [named ongoing task/process] every [interval] until [observable completion or stop condition]. Continue only work already authorized for this task. Stay quiet while state is unchanged or non-actionable; notify on meaningful progress, completion, failure or a specific required input. Record evidence of completion and remove or disable the monitor when done. Keep external messages, spending and access changes within my explicitly stated scope.
Build a bounded feedback loop

Start with triage; expand only after it works.

For [named feedback source] and [named repository], create a first pass that reads new items, deduplicates them and classifies bug, feature request, question or compliment. For actionable bugs, reproduce the issue and prepare a scoped fix in an isolated worktree with relevant checks and a draft PR. You may message [specific recipient/channel] only for [specific purpose], if supplied here. Keep a ledger so repeated runs do not duplicate issues or PRs. Stop at the defined scope boundary and report uncertain cases.
Save the workflow that actually worked

Run after a successful manual task.

Extract a reusable skill from this completed workflow. Include when to use it, required inputs, available tools, steps, evidence checks, known failure modes and the scope of authorized side effects. Generalize the procedure without retaining private data or project-specific credentials. Prefer instructions; add a script only for a deterministic step that benefits from one. Validate the skill and exercise it on one new example.
Build a minimal App Server client

An optional developer track after the operator loop is reliable.

Build a minimal Windows-compatible client for the Codex App Server version installed here. Generate or inspect that version’s protocol schema first. Demonstrate initialization, thread creation, one turn, streamed events, interruption and reconnection or resume where supported. Handle approval requests explicitly and keep the listener local. Use a simple interface; add custom styling after the lifecycle works. Show one runnable end-to-end check and document unsupported behavior.

Practice / operator and developer tracks

Earn the method through evidence.

PASS 1 / CONTEXT → ARTIFACT

Make one repository understandable.

Use a project you care about. Produce a brief, a parts-and-flow manual and one working improvement. Verify the rendered manual against the code.

Pass evidence: source-linked diagram, runnable artifact, main-path check and a resolved defect.

PASS 2 / ACTION → VERIFICATION

Operate one real workflow.

Export a small dataset or prepare a draft form. Choose the actual session, specify the data contract and inspect the resulting object.

Pass evidence: verified fields or schema, counts and boundaries; an exact final state.

PASS 3 / GOAL → REPEATABLE METHOD

Complete one bounded milestone.

Add durable state, a scoped review and a useful deterministic check. Extract a skill only after the workflow works.

Pass evidence: reconciled goals, checks, audit findings and a second successful application of the skill.

A scientific research capstone

Build a scientific replication workbench. Choose a paper with an algorithm you can test on small instances. Ask Codex to recover its mathematical contract, implement a transparent Python baseline and produce an offline HTML that connects inputs, outputs, error checks and source references. This combines Gabriel’s research-goal discipline with Charlie’s architecture and interface discipline.

MilestoneArtifactIndependent acceptance evidence
M1 · ContractAssumptions, objective, constraints, source pages, conventions and a small dataset.A domain review catches ambiguities before coding; every claimed guarantee has a source or is marked unresolved.
M2 · BaselineSimple implementation, input/output example and reproducible commands.Compare to an independent reference or exact enumeration on tractable tiny cases; use domain invariants and justified tolerances.
M3 · ReproductionOne figure or table recreated, with seeds, versions and preprocessing recorded.Explain deviations; distinguish numerical correctness from reproducing the paper’s empirical result.
M4 · PerformanceProfile and a measured bottleneck. Add Rust only if the evidence warrants it.Output parity and deterministic replay where applicable, then benchmark against the same workload and environment.
M5 · WorkbenchBrowsable provenance, results and failure cases; clear project state.Another run reproduces the result from saved instructions; the HTML renders without remote dependencies.
M6 · ReuseA tested replication skill; optional bounded monitor for genuinely ongoing work.A second paper or instance exercises the procedure; repeated runs preserve evidence and do not duplicate actions.

The most useful upgrade: spend more effort making success falsifiable than making the prompt elaborate. An independent oracle, a conservation law, a dimensional check or a valid optimization certificate gives an agent a much stronger signal than “looks good.” This is an adaptation for scientific work, not a capability benchmark claimed by the video.

When to add more agents

Add workers when tasks are independent, their context can be bounded and their outputs can be integrated cheaply. If two workers repeatedly need the same evolving state or edit the same files, the coordination cost may erase the gain. Count accepted evidence and resolved critical-path work, not the number of agents. The workshop’s large agent counts are anecdotes, not a prescription.
